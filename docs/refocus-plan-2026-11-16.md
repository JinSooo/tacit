# Tacit 收敛处理文档（2026-11-16）

给执行者（Codex）的任务书。来源是 2026-11-16 的一次盘点和讨论；数据取自开发机正在运行的后台。

## 0. 执行约定

- 先读根目录 `AGENTS.md`，产品规则以它为准。本文和它冲突时停下来问用户。
- 第 3 节的决定用户已在 2026-11-16 全部确认，并记入 `AGENTS.md`。D6、D7 取代了更早的规则，实现时以新规则为准。
- 本轮不新增功能、配置项、开关。任务里没写的不做；发现值得做的，写进汇报，不动手。
- 先查原因再修。每个质量类任务（T4–T7）第一步都是用给出的样本复现并写明原因，原因和本文推测不一致时以实测为准，并在汇报里说明。
- 一个任务一次提交，提交信息写清改了什么、怎么验证、怎么回滚。
- `./install.sh` 会改本机安装和正在运行的服务，每次运行前要用户同意。删除分支、worktree、数据同样先列清单再等确认。
- 验证命令（仓库根目录）：
  ```sh
  bun test
  bun x tsc --noEmit
  python3 scripts/guarded-run.py --memory-mb 3072 --seconds 240 -- collector/swift.sh test -j 2
  ```
- 不要把记录正文、搜索词、密钥、他人隐私写进提交、文档或汇报；引用样本只写记录 id。
- 每个任务结束汇报：改了哪些文件、验证结果原文、没做或没验证的部分。自报和实测分开写。

## 1. 目标

Tacit 之前从输入出发（能采的都采），没有可以用来拒绝功能的目标。现在改为从产出出发。

**一层整理结果，两个出口：**

| 出口 | 给谁 | 算成功的标准 |
|---|---|---|
| 每日回顾 | 用户本人 | 用户可以停掉自己每晚跑的 Codex“每日对话回顾”自动任务，Notion 日记只需补几句感受 |
| MCP 与会话带入 | Claude Code、Codex 等 | 利用率、命中率、准确率三个指标可量、达标（第 5 节） |

中间那层是“每天发生的事、用户的决定、可点回的原文”。

**来源按离用户意图的远近定角色：**

1. 用户说的、写的（最高）：给 AI 的话、发出的消息、自己的声音、自己写的笔记。
2. 别人对用户说的：聊天里收到的消息、对话里对方的话。
3. 用户看过的（最低）：屏幕、浏览器。只当时间骨架（应用、标题、时长），正文可搜索，不进整理。

对话（AI 会话、微信等聊天、录音）是主体。用户原话：大部分真正的记录来源是对话，由微信或其他聊天组成，另一部分靠录音补充。

## 2. 盘点到的现状

- 记录共 69,380 条：浏览器 49,494、屏幕 7,952、Codex/Claude Code 会话 6,260、git 3,636、微信 1,264、剪贴板 516、文件 132、录音 69、终端 52。条数不代表价值（一场录音是一条）。
- 整理：143 个进行中的事项、84 条未回答的“做完了吗”，项目只有 6 个。说话人条目 387 个，其中 255 个被合并、27 个被忽略。
- 成本：用户记录约 4.1 美元/天，估算 0.3–1 美元，大头是事项详细版。
- Agent 读取（8 天 910 次）：自动带入 543、读详情 263、搜索 48（17 次为空）、查“此刻”40、按时间回看 11、追加 5。11-13 一天 302 次，疑似开发自测。
- 质量样本：
  - “此刻”在用户持续工作时返回“最近 24 小时没有活跃的线程”（2026-11-16 01:29 前后）。
  - 录音 `01M7C5KHNG0HMSKRZ41E2JMMNT`：5 分钟、有效人声 59 秒，拆成 12 个说话人，含乱码短句。
  - 屏幕 `01M7G04C7X4E07HES1DRNFR5NK`：输入过程的每个中间状态各存一行，同一句重复二十多遍。
  - 搜索样本：1 条事项后跟 14 条时长 0–4 秒的窗口切换记录。
- Android：7 个以上分支、约 1.3 万行，是独立应用（本地模型总结、离线识字、短信、通话记录、定位、照片），没有和 Mac 后台配对。
- 工作区：本文写成时约 80 个文件未提交，9 个 worktree、17 个本地分支。
- 已完成未安装：读取审计补记会话、项目、搜索词（见 `AGENTS.md` 2026-11-16 条和 `docs/contracts.md` 4.6）。

## 4. 任务

按顺序执行。

### T0 清理工作区

- 把现有未提交改动按主题分成几次提交（审计补记单独一次）。提交前跑验证命令。
- 列出所有 worktree 和本地分支：最后提交时间、相对 `main` 领先多少、是否已合并。**只列清单，不删除**，交用户决定。
- 完成判据：`git status` 干净；清单交付。

### T1 修两个与时间和环境有关的失败测试

- `hub/test/review-fixes.test.ts`“真实 HTTP 删除立即清理…”：默认时区下在本地凌晨失败，`TZ=Asia/Tokyo` 时通过。查清是测试取日期的方式还是产品代码按天清理的方式有问题；若是产品代码，按生产 bug 处理并留回归用例。
- `plugins/agent-sessions/main.test.ts`“CLI 输出协议…”：第二次运行预期输出 1 行，实际 2 行。原因未查。
- 完成判据：`bun test` 在默认时区和 `TZ=Asia/Tokyo`、`TZ=UTC` 下全部通过。

### T2 让审计补记生效并做统计

- 用户同意后运行 `./install.sh`，然后用一次真实的 MCP 搜索和一次新会话带入，确认 `/v1/audit` 返回的 `args` 里有 `session`、`cwd`、`project`、`q`。
- 删除一条测试记录，确认已有审计的 `q` 被清空（这是删除类改动，要看真实运行结果）。
- 写一个只读脚本 `scripts/agent-metrics.ts`，从 `/v1/audit` 算：
  - 利用率：被带入的会话里，之后有主动查询的比例。带入和查询的会话标识不是同一个值，按工具 + 目录 + 时间窗口关联，脚本输出里写明这个近似。按项目分开，能排除指定项目（如 record-anything 自身）。
  - 命中率：搜索、读取返回空的比例，列出空结果的搜索词。
- 完成判据：脚本对真实数据跑出结果；真实删除验证的输出贴在汇报里。

### T3 Agent 准确率的固定题目集

- 从用户最近 3–5 个真实使用日里起草 20–30 道题，每题有可核对的标准答案和依据记录 id，覆盖：项目进展、某个决定和它的日期、和谁谈了什么、当前卡在哪。
- 题目和答案先交用户确认，再固化。题目文件含个人内容，放数据目录，不进仓库；仓库里只放运行脚本和合成样例。
- 运行脚本通过 MCP 的 `now`、`search`、`get`、`timeline` 作答并打分，输出每题的调用过程。
- 完成判据：用户确认的题目集跑出一份基线分数。

### T4 屏幕记录质量

- 用样本 `01M7G04C7X4E07HES1DRNFR5NK` 复现：输入中的中间状态被逐条保留。目标是同一处文字只留最终稿。
- 查 0–4 秒的窗口切换为什么各自成为一条记录，目标是先合并再入库，或不单独成条。相关规则在 design.md 3.3（屏幕按上下文切换或空闲 2 分钟切开）。
- 已入库的记录不改写（记录写入后不再修改）；只修新采集的。历史数据怎么处理写进汇报由用户决定。
- 完成判据：用同样的操作重录一遍，记录条数和重复行数前后对比；补回归用例。

### T5 搜索结果不被碎片占满

- 依赖 T4 的结论。用 T3 题目集和 T2 的空结果搜索词做前后对比。
- 现有规则是事项、项目排在原始记录前面；问题在原始记录这一段全是同标题短记录。先确认原因再定做法（例如同标题相邻记录折叠成一条）。做法涉及接口返回结构时，先说明影响再动手。
- 完成判据：T3 基线分数不下降，样本查询的前 10 条里重复标题不超过 2 条。

### T6 “此刻”为空

- 复现 2026-11-16 凌晨的情况：有持续活动，`now` 返回“最近 24 小时没有活跃的线程”，而状态页显示 143 个进行中的事项。查整理进程当时是否在跑、事项的最后活动时间是否更新、“此刻”的筛选条件。
- 完成判据：写明原因；修复后有活动时“此刻”非空，或明确显示“有新活动待整理”（这条状态规则已在 `AGENTS.md`）。留回归用例。

### T7 录音可读性

- 用样本 `01M7C5KHNG0HMSKRZ41E2JMMNT` 查说话人为什么拆成 12 个，说话人编号为什么增长到三位字母。
- 查乱码短句的来源（非目标语言、极短片段、低置信度）。
- 按 D7 改为默认只分“我”和“对方”。动手前先说明会影响哪些已确认的声纹、待确认流程和已有说话人数据，已有数据不删。
- 完成判据：原因说明；同一段音频重跑，说话人数量和乱码行数前后对比。

### T8 每日回顾

- 依赖 D8。把现有“日记”产出对齐到四段，并遵守用户提示词里的约束：区分 AI 的方案和用户本人的决定；只提取用户实际表达的内容；没有记录就是未观察到；每条结论能点回原文。
- 来源覆盖 AI 会话、聊天、录音；屏幕和浏览器只提供时间骨架。
- 验证：连续 7 天，和用户的 Codex 每日回顾并排，由用户标出缺了什么、错了什么。
- 完成判据：用户对比 7 天后的结论。

### T9 来源冻结

- 依赖 D5、D9。只做“默认关闭 + 收起入口”，不删代码、不删已有记录。
- 升级时用户已开启的来源如何处理（保持还是关掉），动手前问用户。
- 同步更新 `README.md` 的来源描述。
- 完成判据：全新安装只启用核心来源；已有数据仍可搜索。

### T10 文档

- `docs/design.md` 第 1 节定位改为第 1 节的两个出口；第 11 节验收换成第 5 节。
- `AGENTS.md` 的产品规则分成“核心”和“已冻结功能”两组，内容不改写，只挪位置；新确认的决定各加一条并带日期。
- 完成判据：规则条数前后一致，消失的行逐条能在新位置找到。

### T11 Android

- 依赖 D10，且在 Mac 两个出口验收之后。
- 先出一份清单：现有分支里哪些属于录音、通知、应用使用骨架，哪些冻结；配对和同步缺什么。只出清单，不合并、不删分支。

## 5. 验收
