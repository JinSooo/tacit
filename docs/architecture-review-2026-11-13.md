## 总体判断

分层是清楚的：采集端只读取和持有权限，中枢只收数据，提炼是单独进程，Agent 侧是不加载数据库的薄进程。产品规则（只追加、真删留墓碑、审计不存内容、Host 校验防 DNS 重绑定）在代码里都有对应实现。

主要风险不在分层，而在三处：服务直接跑在源码工作区上、三个进程共用一个不开 WAL 的 SQLite 文件、失败时没有可用的诊断信息。下面按严重程度排。

## 一、高风险

### 1. 正在运行的服务直接执行 git 工作区里的源码（已确认）

`~/Library/LaunchAgents/dev.record-anything.hub.plist` 的启动命令是 `bun <仓库>/hub/src/cli.ts serve`，整理进程和各 AI 工具的 MCP 进程同理；采集端运行插件也是 `bun <仓库>/hub/src/cli.ts run-plugin`（`collector/Sources/Collector/Hub.swift`）。网页由 `<仓库>/web/dist` 提供。

后果：

- 在仓库里改代码、切分支、跑到一半的重构，都会在下一次进程启动时生效。MCP 进程每开一个会话就启动一次，等于改动立刻进入线上。
- `git pull` 之后不重跑 `install.sh`，中枢、整理、采集端三者的版本会不一致；数据库迁移由先启动的那个进程执行。
- 并行 Agent 用 worktree 改代码时主工作区不受影响，但任何直接在主工作区的修改都没有隔离。
- 指向工作区的不止 launchd。`~/.zshrc` 里加的那一行是 `source "<仓库>/plugins/shell/hook.zsh"`（`ShellHook.swift`），每个新开的终端都会执行工作区里的这个脚本；Claude Code 和 Codex 的会话开始钩子、三个 AI 工具的 MCP 注册写的也都是 `<仓库>/hub/src/cli.ts` 的绝对路径（`agents-install.ts`）。仓库挪位置或删掉后，这些地方都会报错，要重新安装和重新连接才能恢复。

建议方向：安装时把中枢代码拷到数据目录或应用包里的固定位置，launchd 和 MCP 都指向那份副本。这会改安装脚本、`collector.json` 的 `repo` 字段和 Agent 注册，属于跨模块改动，先和用户确认。

### 2. 数据库旧副本让“删除就是真删”不成立（已确认）

数据目录里有三个 2026-11-12 的完整数据库副本：`history.db.pre-v9-20261112`、`history.db.pre-v10-20261112`、`history.db.pre-correctness-20261112`，各约 300 MB。它们和主库用同一把密钥，包含副本生成之后被删除的记录。代码里找不到生成它们的地方（`install.sh`、`hub/src`、`scripts` 都没有），应该是手工或某次会话留下的。`db.ts` 自己只在 v1 升级时生成一次 `history.db.bak-v1`，同样没有清理。

问题有两层：

- 产品规则说删除连带原始素材和索引都真删，但副本不在删除流程里，也没有任何界面提到它们。
- design.md 9.2 写“升级时做 schema 迁移，迁移前自动备份”，代码只对 v1 做了；v2 到 v10 的迁移没有自动备份，现在靠手工拷贝。

建议方向：迁移前备份做成统一机制，带保留期（比如迁移成功并运行 N 天后删除），删除记录时如果存在备份要么同步处理、要么在界面上说明。保留期多长需要用户定。

### 3. 失败时没有诊断信息（已确认）

- `server.ts` 的总入口把非输入类异常统一返回“存储操作失败”，不写任何日志。理由是防止密钥经错误通道泄漏，但结果是 500 无从排查。
- `agent.ts` 的读取和追加同样只返回“存储操作失败”。
- 采集端运行插件时 `standardError = FileHandle.nullDevice`（`Hub.swift` 两处），插件失败只剩退出码。
- 整理日志只有 `{"step":"assign","ok":false,"frames":5}` 这样的行，没有原因。今天上午 assign、digest 多轮失败，“此刻”11 小时没更新，从日志看不出是额度、超时还是输出不合 schema。

补充（读完 `llm/index.ts` 后修正）：模型调用的失败原因并没有丢。每次调用都写一行 `llm_usage`，失败时带脱敏后的错误文本，状态页的“最近出错 → 错误详情”显示的就是它。所以整理失败的原因要去状态页看，不在日志里。这次走查没打开状态页，今天失败的原因仍然未知。中枢 500 和插件错误输出两条不受这个修正影响。

建议方向：错误记“类型 + 错误码 + 发生位置”，不记消息正文和请求体；`cli.ts` 里已有 `cliErrorDetail` 这种只输出名称和代码的写法，可以沿用。整理日志的失败行带上失败类别，省得再去查库。

## 二、中风险

### 4. 三个进程共用一个回滚日志模式的 SQLite（已确认现象，影响程度是推断）

`db.ts` 用 `journal_mode=DELETE`，注释里的理由是避免删除后的明文页留在 WAL 里。中枢、整理进程、直接开库的插件运行器都会打开同一个文件。代码里为此做了一圈补偿：

- 中枢把 `busy_timeout` 降到 300 ms，撞锁直接回 503（`cli.ts`）；整理进程设成 30 秒。
- 采集端把 503 当作“留在队列里下一轮再发”（`Hub.swift`）。
- 状态页专门有一行“后台服务忙，自动重试”的计数。

这套补偿能跑，但说明锁竞争是常态。回滚日志模式下读会挡写、写会挡读，数据量越大越明显；中枢是单线程，等锁期间所有请求都停。数据库 5 天已经 344 MB（见第 7 条）。

可选方向，各有代价，需要实测后由用户定：

- 写入都经过中枢，整理进程改为通过中枢接口读写，库只有一个进程打开。
- 改用 WAL，并在删除后做 checkpoint 和截断来处理明文残留。SQLCipher 的 WAL 页也是加密的，注释里担心的“明文页”需要先核实是否成立。

### 5. 采集端的待发送记录只在内存里（已确认，是已知取舍）

`OutboundQueue` 容量 5,000 条，超出丢最旧的；应用退出或崩溃则全部丢失。这是产品规则（Mac 采集端不落盘明文）的直接结果，不是缺陷，但有两个放大因素：

- 每次 `install.sh` 都会重启采集端，升级时队列里的记录直接丢。`applicationWillTerminate` 里有“结束当前活动段、最多等 3 秒把队列发完”的收尾，但 `install.sh` 用 `launchctl bootout` 停进程，发的是 SIGTERM，采集端没有注册信号处理，这段收尾不会执行。正在进行的那一段屏幕记录也一起丢。补一个 SIGTERM 处理走同一段收尾是小改动。
- 第 4 条的锁竞争会让队列在整理忙时积压。

丢弃只在右键菜单里显示“等太久丢掉了 N 条”，主窗口和状态页看不到。建议至少在状态页显示累计丢弃数；是否允许落盘加密缓冲（Android 已经是这个做法）需要用户重新定规则。

### 6. 一个令牌管所有接口（已确认）

`token` 文件（0600）同时用于采集端写入、网页、MCP 进程和插件运行器。拿到它就能读全部记录、读私密内容、删除记录、改设置、改模型配置。

- design.md 7.1 的设想是“Agent 只有一个追加工具”。但 MCP 进程以用户身份运行并读这个文件，一个能执行 shell 的 Agent 可以直接读令牌调用 `DELETE /v1/records/...`，审计里只会记到 MCP 那几个接口的读取。8.5 节讨论了提示注入，没有覆盖这条路径。
- 第三方插件拿到 `HOME` 环境变量（`cli.ts` 的 `plugin-run`），同样读得到令牌，还能调 `/usr/bin/security` 取数据库密钥。设置页已写明“插件代码以你的本机权限运行”，所以这是已告知的风险，但 design.md 4.4 的“插件绕不过去”只对守规矩的插件成立。
- 局域网接入做好之前这只是本机同用户的问题；开放局域网时每台设备需要独立身份，现在的 `device` 是采集端自己填的字符串，中枢只校验格式，不校验和记录里的 `device` 一致。

建议方向：至少把 Agent 用的令牌和管理用的令牌分开，Agent 令牌只能访问 `/v1/agent/*`。挡不住读钥匙串的恶意程序，但能挡住被注入的 Agent 顺手删库。

### 7. 数据库增长速度没有预算（已确认大小，原因未查）

`history.db` 344 MB，启用日期是 2026-11-08 前后，其中包含一次历史导入。design.md 没有容量估算，也没有任何清理或归档策略；History 的规则是只增不改。按这个量级一年会到十几到几十 GB，全文索引、`secure_delete`、回滚日志都会随之变慢。

需要先量：各表和索引各占多少（屏幕记录正文、FTS、活动片段、模型用量），日增量在不导入的日子是多少。数据库加密，这次没有打开看。

### 8. 搜索只支持整句短语（已确认）

`db.ts` 的 `list` 把整个查询串做成一个 FTS 短语：“登录 修复”只匹配这两个词相邻出现的记录，不是“同时包含”。单个汉字退回 `LIKE` 全表扫描。Agent 的 `search` 走同一条路，事项和项目是 `instr` 子串匹配。

对人来说搜两个关键词搜不到会以为没记录；对 Agent 来说它习惯用多个词检索，命中率会很低。改成按空白拆词后 AND 组合是小改动，但会改变现有搜索结果，先确认。

### 9. 提炼链路依赖订阅 CLI 的内部行为（已确认）

`codex-cli.ts` 为了省 token 和绕开 WebSocket，覆盖了 codex 的模型目录、关掉十多个 feature 开关、自定义了一个指向 `chatgpt.com/backend-api/codex` 的 provider，并靠 `codex login status` 输出里的“using ChatGPT”字样判断登录方式。这些都不是稳定接口，codex 升级后任何一处变化都会让整理静默失败（配合第 3 条，失败原因还看不到）。launchd 的 PATH 里写死了 `codex/0.166.0` 的路径，升级 codex 后要重跑安装。

`AGENTS.md` 已记录“以后换成单独的 API 通道”。在那之前，建议把“整理连续失败”做成用户看得见的状态，并在升级 codex 后有一次自检。订阅账号能否这样自动调用，design.md 第 13 节仍列为未核实。

## 三、低风险和可维护性

### 10. `server.ts` 的路由是一个 120 行的 if 链（已确认）

所有接口在 `createHandler` 的一个函数里顺序判断，每个请求都新建 `AgentReads`、`AudioStore`、`DistillStore`。参数校验内联在路由里（例如 `/v1/facts` 那一段）。现在 30 多个接口还读得下去，加上配对、设备同步后会难以维护。可以按领域拆成路由表，和 `settings.ts` 已有的做法一致。

### 11. 时间戳两种写法混用（已确认）

记录的 `t_start`、状态接口用带时区的本地时间（`toLocalIso`）；`t_received`、`agent_reads.at`、事实的 `created_at`、墓碑的 `deleted_at` 用 `toISOString()`（UTC）。`status.ts` 算“今天”时为此多查一天再用 `Date.parse` 过滤，结果是对的，但每个新查询都要记得这件事。按字符串比较和排序的地方只要混进另一种写法就会错。建议统一成一种并在 `contracts.md` 写明。

### 12. 记录类型没有按设计从 Schema 生成（已确认）

design.md 3.2 写“格式只在一份 JSON Schema 里定义，生成 Swift、Kotlin、TypeScript 三端类型”。仓库里 `schema/record.schema.json` 存在，但 `packages/record/index.ts` 和 `CollectorCore/Record.swift` 都是手写的，没有生成脚本。字段不一致目前靠中枢入库校验兜底，Swift 端写错字段要到运行时被拒收才知道。

### 13. 数据库文件权限比其他文件宽（已确认）

`history.db` 是 0644，三个副本、`token`、`hub.json` 是 0600。目录本身 0700 且文件加密，实际影响小，但应当一致。同目录的 `collector-status.json`、`collector.json` 也是 0644。

### 14. `device` 写死（已确认）

`agent.ts` 里 `AGENT_DEVICE = "mac"`，采集端默认也是 `"mac"`，design.md 的例子是 `mac-m5`。第二台 Mac 接入时两台会同名。等做配对时一起处理即可，现在只需要知道这里有个假设。

### 15. MCP 进程数量（已核对，不是泄漏）

走查时看到 8 个 `mcp --tool codex` 进程。核对后它们的父进程是同一个仍在运行的 codex 进程，启动时间分散在今天上午，对应它开过的各个会话。`agent-cli/mcp.ts` 的主循环读 stdin，读到结束就退出，所以父进程关掉它们时会正常结束。每个进程是一个不加载数据库的薄进程，占用不大。这条不需要处理。

### 提炼

#### 16. 删除记录后，模型写的文字要等下一次整理成功才消失（已确认，高风险）

`store.ts` 的 `removeRecord` 在删除事务里立刻做了三件事：删掉引用这条记录的事实、从详细版里去掉引用它的原话、把相关事项、项目和当天日记标成待重写。但事项的标题、详细版里的目标和进展、简略版，项目的简略版，当天的日记，以及“此刻”，这些模型写出来的文字原样留着，直到下一次每小时那轮整理成功重写。

这段时间里它们照常显示，也照常自动带入给 AI 工具。模型连不上时（比如今天上午）会一直留着。这和“删除就是真删，连带重新生成引用它的提炼结果”有差距：重新生成是排了队，不是完成了。

建议方向：删除时把受影响对象的简略版和详细版正文立即清空或标记为不可展示、不可带入，等重写完成再恢复。会让界面短暂出现“正在重新整理”，需要用户确认这个表现。

#### 17. 修正记录没有进入提炼（已确认代码里没有处理，后果是推断）

产品规则是“显示和提炼都以修正为准”。提炼给模型看的片段由 `run.ts` 的 `frameView` 生成，它取的是原记录的标题和正文；`distill/` 下没有任何地方读 `corrects` 字段。修正记录本身的来源是 `manual.correction`，`frames.ts` 会把 `manual.*` 记录单独切成片段，所以模型看到的是：原记录的错误内容照旧，另外在修正发生的时间点多出一条孤立的手动记录。

#### 18. “此刻”取决于单条事项的整理是否成功（已确认）

`nowStep` 不调模型，“此刻”就是最近有活动、且已有简略版的那条事项的简略版，更新时间取这条事项上次整理成功的时间。事项的详细版和简略版只在每小时那轮写，每轮最多 12 条，任何一步失败这条事项就留到下一小时。

两个后果：

- 新开始做的事，最快也要等到下一个整点轮次才出现在“此刻”，最坏情况超过 1 小时。design.md 的验收口径是“注入的简略版落后最新活动不超过 1 小时”，按现在的节奏设计上就卡在边界。
- 排在最前的那条事项整理失败时，“此刻”显示的是它的旧内容和旧时间，没有任何失败提示。这就是走查时看到“11 小时前更新”的机制。

#### 19. 一次失败可能停掉整轮（已确认代码，实际触发情况是推断）

- `run.ts` 的熔断用正则 `/limit|quota|rate.?limit|usage|exceeded|429|额度|限额/i` 判断是不是额度问题，命中后本轮剩下的调用全部跳过。读完 `llm/process.ts` 和 `llm/http.ts` 后补充：本项目自己生成的超时报错是中文（“模型调用超时……已终止进程”），不会命中；HTTP 429 会命中，这是对的。风险在 CLI 后端：`codex` 或 `claude` 非零退出时，报错文本取的是它们 stderr 的前 500 个字符，里面只要出现 `limit`、`usage`、`exceeded` 任何一个词（不一定是额度问题），整轮就停。实际有没有误触发要看状态页里的错误文本。
- 归属步骤（`assignStep`）按时间顺序分批，任何一批失败就 `break outer`，后面的批次这一轮都不做。如果最早那批因为内容本身的原因反复失败，后面的片段会一直排不上。今天的日志里同样的 5 个片段连续 4 轮失败，之后成功，看起来是暂时性的，但这个结构没有跳过坏批次的办法。
- 模型调用没有重试，失败就等下一轮（15 分钟或 1 小时）。

#### 20. 删除的代价随事项长度增长（已确认，低风险）

- 事项里只要有一条记录被删，这条事项就整条重建：把它名下所有片段的全文重新分批喂给模型。持续几周的事项删一条记录，要重放全部历史。
- `removeRecord` 每删一条记录都把所有事项和项目的详细版读出来解析一遍找原话。插件卸载选“删除它的全部记录”时是逐条调删除接口（`plugin-manager.ts` 的 `uninstall`），几千条记录就是几千次全表扫描，期间还占着写锁。

#### 21. `ignored` 一个状态两种含义（已确认，低风险）

片段被模型判为零碎活动时标 `ignored`；片段进了“候选事项”（还没攒够 15 分钟或两段）时也标 `ignored`。候选一天没攒够就过期，这些片段不会再被看第二次。状态页“已忽略”的计数因此包含了两类东西。按规则这些内容只进日记是对的，但状态上分不清，以后想回头重新归属时没有依据。

#### 提炼里做得好的

- 模型调用都在事务之外，落库是小事务，单步失败不影响其他步骤。
- 事实必须带逐字依据，依据要能在原记录里找到；原话同样逐字校验，AI 会话里只认用户发言（`groundedQuote`、`keepGroundedFacts`）。
- 用户写的事实模型推翻不了；高置信度的“推测”直接丢弃，不会被当成已定。
- 私密记录的标题和正文不发给模型，整段都是私密时只给应用和时长。
- 简略版单独一次调用，输入只有详细版，拿不到原始记录。
- 所有系统提示词开头都有同一段不可信数据规则，原始内容包在 `<data>` 里。

### 密钥拦截和采集前过滤

#### 22. 隐私窗口靠窗口标题识别，需要实测（代码已确认，是否漏判是推断）

`Policy.swift` 用窗口标题里是否含 “Private Browsing”“Incognito”“无痕”“隐身”等字样判断浏览器隐私窗口。采集端读到的窗口标题是辅助功能给的窗口标题，通常就是网页标题，不一定带这些字样；各浏览器、各语言、各版本的写法也不同。如果识别不到，隐私窗口里的内容会被正常记录。设置页写的是“按窗口标题识别”，用户会以为这是可靠的。

需要在 Safari、Chrome、Arc、Firefox、Edge 的中英文界面下各开一个隐私窗口实测。

这次试过一次，没有结论：我开了一个 Chrome 无痕窗口访问 example.com，打算看它会不会出现在记录里。但当时电脑处于空闲状态（最后一条屏幕记录停在 13:28，空闲超过 2 分钟采集端不读屏幕），这个窗口没有机会被采集，所以既不能说明识别有效，也不能说明无效。想直接读窗口标题也没成：命令行没有辅助功能权限。测试用的 Chrome 已经关掉。

这个测试需要有人在电脑前操作：打开隐私窗口，在里面停留十几秒并动一下鼠标，切到别的应用，然后在历史记录里搜这个页面的标题。搜得到就是没拦住。

#### 23. 黑名单应用的窗口先被读进内存再丢弃（已确认，低风险）

`main.swift` 的 `tick` 先调 `ax.snapshot` 读完整个窗口的文字，再用应用标识和窗口标题判断要不要跳过。密码管理器在前台时，它窗口里的文字已经读进采集端内存，只是没有发出去。应用标识在读之前就知道，把这一半判断提前即可；窗口标题那一半确实要读了才知道。

另外 design.md 8 节的黑名单写了“银行”，代码里只有钥匙串访问、密码 App 和 6 个密码管理器，没有银行类应用，也没有 KeePassXC、Enpass 这类常见的。黑名单目前只读展示，用户不能自己加。

#### 24. 密钥规则的覆盖范围（已确认）

`redact.ts` 的规则和验收口径一致：私钥块、AWS、GitHub、Anthropic、OpenAI、Slack、Stripe、Google、GitLab、HuggingFace、JWT、Bearer 后的值、URL 里的密码、`key=` 类赋值（要求 16 位以上、两类字符、熵不低于 3.5），加上剪贴板里单独复制的密码。没有固定格式的串拦不住，是已记录的边界。

三个没被口径覆盖的点：

- 只处理 `title`、`body`、`context`，`people`、`media` 不过规则。目前这两个字段不放自由文本，影响小。
- 拦截只在中枢入库时做。之前的明文存在于采集端内存、终端钩子的缓冲文件、本机 HTTP 请求里。这是已知取舍，但 design.md 8 节“密钥从不落盘”对终端钩子的缓冲文件不成立（`AGENTS.md` 已单独说明明文最多留到下一次成功入库）。
- 采集端会截断过长的正文（剪贴板 2 万字、屏幕每段 10 万字）。密钥刚好跨在截断点上时，剩下的半截不再匹配规则。概率低，推断，没有构造用例验证。

### 插件

#### 25. 第三方插件没有隔离，和设计的差距（已确认）

运行方式：`bun --no-install --no-env-file <入口>`，环境变量只给 `PATH`、`HOME`、`TMPDIR` 和配置，工作目录是插件代码目录。没有沙箱，插件能读写用户目录下的任何东西（第 6 条已说明它能拿到令牌）。安装界面写明了这一点。

和 design.md 4.4 的差距：

- 从 git 安装时没有记下提交号，更新时也不显示改了什么。预览到安装之间有内容哈希校验，防的是这段时间内文件被换，不是防上游变更。design.md 第 14 节把“要不要校验签名或固定提交”列为未定。
- 配置项只有文本、数字、开关三种，没有“密钥”类型；而且普通配置里一旦检测到疑似密钥就拒绝保存。需要 API key 的插件目前没有合规的配置办法。
- 清单没有平台、运行方式（定时、持续、手动导入）、能否导入历史这几个字段。

做得好的：安装走暂存目录加原子改名，拒绝符号链接和特殊文件，限制 25 MB 和 2,000 个文件；git 克隆关掉钩子和危险协议；插件产出的记录只能用自己的来源名；插件要求删除的缓冲文件只能在数据目录的 `buffer/` 下；增量位置只在整次运行零拒收、零协议错误时才写入。

### 音频

#### 26. 录音、人声检测、加密写盘都在一个串行队列上（已确认结构，丢帧频率未知）

`AudioCoordinator` 的 `queue` 同时处理：两路音频每 10 毫秒一次的回调、人声检测、片段加密写盘、每段都重写一次的元数据文件、每秒一次的状态检查、每 30 秒一次的保留期清理和状态发布。回调用一个 400 格的信号量做背压，约 4 秒处理不过来就判定“音频处理跟不上，已停止该路录音”，至少 60 秒后才重试。

代码注释记录了这件事发生过（扫描全部对话元数据拖慢队列导致停录），当时的修法是把扫描限成每分钟一次。但 `publish()` 仍然每次都扫全部对话的元数据，它每 30 秒以及每次状态变化都会在这个队列上跑。保留期 7 天时对话数有上限，问题不大；保留期调到 365 天（设置允许）时这个扫描会变重。

已核对日志：`collector.log` 里“跟不上”只出现在 2026-11-09 23:11 到 23:26 这一段，是同一次事件，当时转写进程正在运行；之后到今天没有再出现。所以这是发生过一次、已经缓解的问题，不是持续在丢。优先级可以放低，保留期调大之前再处理。

日志开头还有 12 次采集端崩溃，原因都是系统声音录音启动时的未捕获异常（“Failed to create tap due to format mismatch”），发生在 11-09 之前。现在的启动保护就是为它加的：崩溃后下次不自动开录音。保护只防止反复崩溃，那一次崩溃本身仍会带走内存里的待发送记录（第 5 条）。

#### 27. 说话人合并规则有两份实现（已确认，低风险）

`hub/src/audio.ts` 的注释写明合并阈值“与采集端 `WorkerLogic.consolidate` 一致”。同一套规则在 TypeScript 和 Swift 里各写了一遍，Android 接入后是第三遍。改一处忘改另一处，两端对“谁是谁”的判断就会不同。至少把阈值放进一份共享的数据文件，或者加一组两端共用的测试向量。

#### 音频里做得好的

- 启动保护：上次开启录音时崩溃，下次启动不自动录，要用户手动打开。
- 每路录音带代次标记，切换设备后旧回调的帧直接丢弃，不会串到新会话。
- 转写是单独的低优先级进程，崩溃后隔 10 分钟再启动，不会卡在同一段对话上反复重试。
- 中枢删除对话后，设备在下次同步时删除音频并回执；转写进程占用期间不删。
- 音频片段在内存里编码成 AAC，再用 AES-GCM 加密后写盘，每段一个随机 nonce；解码也在内存里做，全程没有明文音频文件。目录和文件都拒绝符号链接。
- 转写进程对没有用户声音的对话只算声纹、不转写；非会议时系统声音那一路不转写进记录，只用来去回声。和产品规则一致。
- 转写失败最多重试 3 次，失败信息只写“音频处理失败”，不带底层异常。

#### 28. 声纹和对话元数据在磁盘上是明文（已确认）

音频片段是加密的，但同一目录下的两个文件不是：

- `speakers.json`（转写进程的缓存）：每个说话人的声纹向量、各时间窗口的归属，以及中枢返回的说话人名字。代码注释说它“不保存文字或明文音频”，这是对的，但声纹本身是生物特征，名字是真实姓名。
- `meta.json`：每段对话的起止时间、每个片段的时间和响度、当时在用的会议软件。

文件权限是 0600，目录 0700，和令牌文件同一级别的保护。design.md 8 节说“数据库和原始素材加密”，这两个文件算不算原始素材没有定义。它们随音频一起按保留期删除。

#### 29. 每段对话结束都启动一次转写进程（已确认，性能）

`collector.log` 末尾全是这样的行：`skipped segments=1 seconds=1.3 peak_rss_bytes=637911040`。只有一个片段、最后被跳过的对话，也要启动进程、加载模型，占约 640 MB 内存跑一两秒。11-12 为了缩短转写延迟，把“对话一结束就启动”改成了默认行为。零碎的短声音多的时候，这会是采集端开销里的大头，和验收里的 CPU 口径直接相关。可以考虑片段太少、太短的对话攒一批再处理。

### 屏幕读取

没有发现结构性问题。每次扫描有元素数、时间和深度上限；安全输入框激活时不读；空闲超过 2 分钟结束当前段；OCR 只在辅助功能读不到正文时才用，同一段 15 秒内最多一次；OCR 结果回来时如果已经换了窗口就丢弃。两个相关问题已写在第 5 条（SIGTERM）和第 23 条（先读后判）。

### 第三轮补读的其他发现

#### 30. 连接 AI 工具时留下的配置备份不清理（已确认）

`agents-install.ts` 每次改 `~/.claude/settings.json`、`~/.codex/hooks.json`、`~/.codex/config.toml`、Claude Desktop 的配置之前，都会在原目录留一份 `.ra-backup-<时间>-<随机串>` 副本。本机现在有 6 份。`config.toml` 里可能有用户其他服务的凭据，副本会一直留着。读过的代码里没有清理它们的地方。备份本身是对的，缺的是保留上限。

#### 31. 同一个提交在多个 worktree 里各记一条（已确认）

查最近记录时看到：同一个提交（同一个哈希）在 13:16 记了 3 条，分别来自 `record-anything-android-complete`、`-android-sources`、`-android-sources-v2` 三个工作目录。git 插件的去重键是“目录:哈希”。用 worktree 并行开发时（这个项目自己就这么做），每个提交会按 worktree 数量重复，时间轴上是噪声，提炼时也多读几遍。去重键改成“仓库主目录:哈希”即可，`distill/repos.ts` 里已经有把 worktree 解析到主仓库的逻辑。

#### 32. 读取审计先排在内存里（已确认，低风险）

`agent-audit.ts` 把审计行先放进内存队列，写库不等锁，失败就 2 秒后重试，上限 1 万行。中枢崩溃或被杀时，还没写进去的审计会丢。产品规则是“每次读取留审计记录”。正常情况下延迟只有几秒，丢失只发生在锁竞争叠加进程异常退出时。

#### 33. 其他小项（已确认）

- Anthropic 接口的调用把 `max_tokens` 写死为 8192（`llm/http.ts`）。事项详细版输出超过这个长度时会被截断，判为“未返回完整结构化结果”而失败。
- 三份日志都不轮转。目前都很小（最大的 `distill.log` 171 KB），长期运行后需要上限。`collector.log` 里还留着早期调试版本打的探针行。
- MCP 服务是手写的 JSON-RPC 处理，不是 design.md 技术栈表里写的官方 SDK。功能上没问题，协议升级时要自己跟。
- 终端钩子只支持 zsh。命令以空格开头时不记录，这是个有用的习惯，但界面上没有告诉用户。

#### 这一轮看到做得好的

- 安装脚本下载语音模型和推理库时逐个校验 sha256，先放暂存目录，校验通过才替换。
- 连接 AI 工具前先生成改动预览；写入是“临时文件加改名”；发现同名配置不是自己写的就拒绝覆盖；Codex 里只读工具默认免确认，写入工具每次都要用户确认。
- 调用 `codex`、`claude` 时只传白名单里的环境变量，不会因为是谁启动的整理进程而走到别的中转站。
- API key 只进钥匙串，配置文件校验时遇到未知字段直接拒绝；测试连接的错误文本过一遍密钥规则再返回。
- 会话开始钩子 2 秒超时，中枢没起来时不会卡住 AI 工具启动。

## 五、和设计一致、做得好的地方

留作基线，改动时不要破坏：

- Host 头校验在鉴权之前，被拒请求不写审计，网页有 CSP，静态文件防目录穿越（`server.ts`）。
- 审计只存参数长度、id 和字节数，不存检索词和返回内容，记录真删后审计里不留内容（`agent.ts`）。
- Agent 追加只增不改，按外部标识或内容哈希去重，用户删过的不再写入，内容变了挂修正（`agent.ts` 的 `append`）。
- 删除时同时删修正记录、全文索引，写墓碑，通知提炼层重新生成（`db.ts` 的 `delete`）。
- 模型 CLI 调用关闭工具、只读沙箱、不保存会话、忽略用户配置（`codex-cli.ts`、`claude-cli.ts`）。
- MCP 和 hook 命令走单独的入口，不加载数据库和模型模块（`cli.ts` 开头）。
- 插件运行排在一个串行队列里，同一插件不会并发（`Hub.swift` 的 `PluginScheduler`）。
- 数据库密钥读不到时报错退出，不会生成新密钥覆盖（`config.ts`）。
